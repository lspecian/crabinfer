<objective>
Implement the Marlin-style fused dequant+GEMM CUDA kernel for GPTQ/AWQ INT4 inference, targeting 1.5-2x throughput improvement over the naive dequant-then-matmul path on RTX 3060.

Purpose: QLOAD-03 — the fused kernel eliminates the intermediate FP16 weight materialization, directly dequantizing INT4 packed weights into Tensor Core registers during GEMM. This is the single highest-impact performance optimization for quantized model serving.
Output: Marlin CUDA kernel in paged_attention.cu, KernelBackend trait method, CudaBackend implementation, weight reformat in quantization.rs, and GptqLinear dispatch.
</objective>

    This is the most complex task in Phase 1. Implement in four parts:

    **Part A: Marlin weight reformat (CPU, in quantization.rs)**

    Replace the `reformat_for_marlin` stub with the actual implementation:

    ```rust
    pub fn reformat_for_marlin(&mut self, backend: &dyn KernelBackend) -> Result<bool> {
        // Only reformat on CUDA backend
        if backend.name() != "cuda" { return Ok(false); }

        let (pack_rows, out_features) = self.qweight.dims2()?;
        let in_features = pack_rows * 8;

        // Alignment check: Marlin requires N % 64 == 0 and K % 16 == 0
        if out_features % 64 != 0 || in_features % 16 != 0 {
            tracing::warn!("Skipping Marlin reformat for layer with N={out_features}, K={in_features} (alignment)");
            return Ok(false);
        }

        // Reformat on CPU then transfer to device
        let qw_cpu = self.qweight.to_device(&Device::Cpu)?;
        let qw_data: Vec<u32> = qw_cpu.to_vec1()?; // Flatten to 1D

        // ... Marlin tile shuffle algorithm ...
        // The key insight: rearrange INT4 weights so that each warp's 8 weights
        // are contiguous in memory, and interleaved within u32 for efficient
        // Tensor Core extraction.
        //
        // Tile layout: [K/16, N/64, 128] u32
        // Each 128-u32 tile contains a 16x64 block of INT4 weights (16*64/8 = 128)
        // Within the tile, the 8 INT4 values packed in each u32 are interleaved
        // in pattern 6,4,2,0,7,5,3,1 (bit positions) for Tensor Core MMA.

        let marlin_data = reformat_gptq_to_marlin(&qw_data, in_features, out_features);
        let marlin_tensor = Tensor::from_vec(marlin_data, (in_features / 16, out_features / 64, 128), &Device::Cpu)?
            .to_device(self.qweight.device())?;

        self.qweight_marlin = Some(marlin_tensor);
        Ok(true)
    }
    ```

    Implement `reformat_gptq_to_marlin(qw: &[u32], K: usize, N: usize) -> Vec<u32>`:
    - For each 16xN tile of the weight matrix (16 input features, N output features):
      - For each 16x64 sub-tile within that row of tiles:
        - Pack the INT4 values into Marlin's interleaved layout
        - The interleaving pattern within each u32: bits [3:0]=w6, [7:4]=w4, [11:8]=w2, [15:12]=w0, [19:16]=w7, [23:20]=w5, [27:24]=w3, [31:28]=w1
        - This pattern allows `(packed >> (lane * 4)) & 0xF` in the kernel to extract the correct weight for each Tensor Core lane

    NOTE: The exact interleaving pattern should be validated against the Marlin paper. If the above pattern is incorrect, use the simpler approach: keep the same GPTQ packing order but rearrange which weights go into which u32 so that each warp's computation reads contiguous memory. The fused kernel then handles the extraction.

    **Alternative simplified approach (recommended for Phase 1):** Instead of the full Marlin interleaving, use a simpler tile reformat that just rearranges the GPTQ qweight tensor so that the 16x64 tiles are contiguous in memory (row-major within each tile, tiles laid out in [K/16, N/64, 128] order). The CUDA kernel then reads tiles efficiently via `cp.async` or simple coalesced loads. This gives most of the memory bandwidth benefit without the full interleaving complexity. The full interleaving can be added in Phase 2 if profiling shows it matters.

    **Part B: Marlin CUDA kernel (in paged_attention.cu)**

    Add after the existing `gptq_dequant_f32` kernel:

    ```cuda
    // Simplified Marlin-style fused dequant+GEMM kernel for sm_86 (Ampere).
    //
    // Each thread block handles a 16x64 output tile.
    // Weights are pre-reformatted into [K/16, N/64, 128] tile layout.
    // The kernel loads weight tiles, dequantizes INT4 to FP16, and accumulates
    // via FP16 FMA (not full Tensor Core MMA — that's a Phase 2 optimization).
    //
    // This is simpler than the full Marlin kernel but still fused: no intermediate
    // dequantized weight tensor is materialized in global memory.
    ```

    Implement `marlin_gemm_f16` as an `extern "C" __global__` kernel:
    - Grid: (N/64, M, 1) where M = batch size, N = out_features
    - Block: (256, 1, 1) — 8 warps per block
    - Each block computes a [1, 64] output tile (one batch row, 64 output columns)
    - Loop over K in steps of 16:
      - Load 16x64 weight tile from reformatted qweight (128 u32 values)
      - Dequantize: extract INT4 from u32, subtract zero point, multiply by scale
      - Multiply by input activation and accumulate
    - Write output tile to global memory
    - Shared memory: load input tile [1, 16] and weight tile [16, 64] for reuse

    Signature:
    ```cuda
    extern "C" __global__ void marlin_gemm_f16(
        __half* __restrict__ output,           // [M, N]
        const __half* __restrict__ input,      // [M, K]
        const unsigned int* __restrict__ qw,   // [K/16, N/64, 128] Marlin tile layout
        const __half* __restrict__ scales,     // [K/group_size, N]
        const unsigned int* __restrict__ qzeros, // [K/group_size, N/8]
        int M, int N, int K, int group_size
    );
    ```

    IMPORTANT: Do NOT use `mma.sync` PTX instructions in Phase 1 — they require `-arch=sm_86` NVRTC flag and careful register management. Use standard FP16 FMA (`__hfma`) instead. This is still fused (no global memory intermediate) and avoids NVRTC compilation issues. The full Tensor Core MMA path is a Phase 2 optimization.

    **Part D: CudaBackend implementation (in cuda_backend.rs)**

    Add `marlin_gemm()` implementation to CudaBackend's KernelBackend impl:
    - Extract storage pointers from input tensors (same pattern as `gptq_dequantize`)
    - Compute grid/block dims: grid = (N/64, M, 1), block = (256, 1, 1)
    - Shared memory: (16 * 64) * sizeof(half) for weight tile + 16 * sizeof(half) for input = ~2176 bytes
    - Launch `marlin_gemm_f16` kernel
    - Return output tensor [M, N] in F16

    Also add `-arch=sm_86` to the NVRTC compile options in `CudaBackend::new()` to enable FP16 arithmetic intrinsics. Add it to the existing `options` vec alongside the include flag.

    **Part E: GptqLinear forward dispatch (in quantization.rs)**

    Update the `forward()` method to use Marlin when available:
    ```rust
    fn forward(&self, xs: &Tensor) -> Result<Tensor> {
        if let Some(ref qw_marlin) = self.qweight_marlin {
            // Try Marlin fused path via thread-local or global backend
            // NOTE: The backend is not directly accessible from Module::forward().
            // Two options:
            // 1. Store a reference to the backend in GptqLinear (lifetime issues)
            // 2. Use a thread-local global (set by engine loop)
            // 3. Pass backend through a different mechanism
            //
            // For Phase 1, use approach: check if device is CUDA and try direct
            // kernel launch via the CudaBackend.
            // Actually, the cleanest approach is to add an optional backend Arc
            // to GptqLinear at construction time.

            // Fallback: use CudaBackend directly if on CUDA device
            #[cfg(feature = "cuda")]
            if xs.device().is_cuda() {
                // Access the global CUDA backend (same pattern as fused kernels)
                if let Ok(result) = crate::serving::kernels::cuda_backend::CudaBackend::marlin_gemm_direct(
                    xs, qw_marlin, &self.scales, &self.qzeros, self.group_size
                ) {
                    return Ok(result);
                }
            }
        }

        // Naive fallback: dequantize then matmul
        let w = self.dequantize(xs.dtype())?;
        let result = xs.matmul(&w.t()?)?;
        match &self.bias {
            Some(b) => result.broadcast_add(b),
            None => Ok(result),
        }
    }
    ```

    For the CudaBackend dispatch, add a `pub fn marlin_gemm_direct(...)` static method to CudaBackend that gets or creates a thread-local CudaBackend instance and calls `marlin_gemm()`. This avoids passing the backend through the Module trait.
