pub fn verify_sha256(file_path: &std::path::Path, expected_hex: &str) -> anyhow::Result<()>;

From hf-hub 0.5.0 (crate API — Siblings struct has only `rfilename`, no per-file SHA):
```rust
pub struct Siblings { pub rfilename: String }
pub struct RepoInfo { pub siblings: Vec<Siblings>, pub sha: String }
```

IMPORTANT: The `hf-hub` `Siblings` struct does NOT include per-file SHA-256.
The HF API JSON response DOES include `lfs.sha256` for LFS files (safetensors are LFS).
To get per-file LFS SHA-256, we must either:
  (a) Make a direct HTTP request to `https://huggingface.co/api/models/{repo_id}` and parse `siblings[].lfs.sha256`, OR
  (b) Compute SHA-256 and store it in a local manifest for re-verification on subsequent loads.

Approach (a) is preferred because it validates against the authoritative source.

    - Test 4: New unit test: `fetch_lfs_sha256_map` returns empty map for files without LFS metadata (config.json, tokenizer.json)

  <action>
1. Add a helper function `fetch_lfs_sha256_map(repo_id: &str) -> anyhow::Result<HashMap<String, String>>` that:
   - Makes an HTTP GET to `https://huggingface.co/api/models/{repo_id}` (using reqwest, which is already a dependency via hf-hub)
   - Reads the `HF_TOKEN` env var and adds it as `Authorization: Bearer {token}` header if present (for gated models)
   - Parses the JSON response, iterating `siblings` array
   - For each sibling with a `lfs.sha256` field, inserts `rfilename -> sha256` into the map
   - Returns the map (empty if API call fails — we log a warning and skip verification rather than blocking download)

2. In `ensure_model_cached`, after the file listing fetch and before the download loop:
   - Call `fetch_lfs_sha256_map(repo_id).await` and store the result
   - If the call fails, log `tracing::warn!("Could not fetch LFS checksums for {repo_id}, skipping SHA-256 verification")` and continue with an empty map

3. In the download loop, after each successful `repo.get(filename)` call that returns `local_path`:
   - Check if `lfs_sha_map` contains `filename`
   - If yes AND the file ends with `.safetensors`: call `verify_sha256(&local_path, &expected_sha)?`
   - This propagates the error up, aborting the download with a clear "SHA-256 mismatch" message
   - Log `tracing::info!("SHA-256 verified: {}", filename)` on success

4. For the `fetch_lfs_sha256_map` helper, use `reqwest::Client` directly (not hf-hub's client). The function should be `#[cfg(feature = "providers")]` gated like `ensure_model_cached`. Parse the JSON with `serde_json::Value` to avoid creating new struct types — just navigate `value["siblings"][i]["lfs"]["sha256"]`.

5. Add unit tests:
   - `test_parse_lfs_sha256_from_json`: Create a sample JSON string mimicking the HF API response with 3 siblings (one safetensors with LFS sha256, one config.json without LFS, one pytorch_model.bin with LFS). Call a pure parsing helper and verify the map contains the expected entries.
   - Extract the JSON parsing into a separate pure function `parse_lfs_sha256_map(json: &serde_json::Value) -> HashMap<String, String>` so it can be tested without HTTP.

NOTE: Use `reqwest` which is already an indirect dependency. Check Cargo.toml — if reqwest is not a direct dependency of crabinfer-core, add it with `features = ["json"]` under `[dependencies]` gated by the `providers` feature flag.
